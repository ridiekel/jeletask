## Before you upgrade

- The bridge uses the HiveMQ MQTT client instead of Eclipse Paho. It still speaks MQTT 3.1.1, but no longer falls
  back to the older MQTT 3.1: the broker has to support MQTT 3.1.1. Every mosquitto since 1.3 (2014) and the Mosquitto
  add-on of Home Assistant do.
- A password without a username (`TELETASK_MQTT_PASSWORD` without `TELETASK_MQTT_USERNAME`) is no longer sent: MQTT
  3.1.1 only allows a password together with a username, and mosquitto closed such a connection without an answer.
  The bridge now connects without credentials and logs a warning.
- Commands that arrive while the central unit is unreachable are dropped after 30 seconds, see below. Automations that
  relied on a command still being executed after a long outage have to send it again.

## New

- A display message (`DISPLAYMESSAGE`) is now a `notify` entity in Home Assistant. `notify.send_message` shows the
  text on the displays, split over the two lines. See [MESSAGES.md](../MESSAGES.md#from-home-assistant).
- A display in `config.json` can have a default `message_type` (`message` or `alarm`), `message_beeps` (0 to 255) and
  `ascii` (`true`: 16 ASCII characters per line, `false`: 8 of any kind), for a display message that does not say. All
  are optional; without them a message stays a unicode alarm with one beep. Home Assistant only passes the text, so
  set them for the displays you use from Home Assistant.
- A line of a display message that is too long for the display is still cut off, but now with a warning in the log
  (`Display message 1000 line 2 '...' has 28 characters, the display shows 16 with ascii: cut to '...'`).
- Every image carries the licence of jeletask (GPLv3) and the notices and licence texts of the libraries inside, under
  `/licenses`. `THIRD-PARTY.txt` lists every library with its version and licence.

## Fixed

- A `DISPLAYMESSAGE` in `config.json` no longer stops the bridge from starting. The Home Assistant discovery ended
  in a `NullPointerException` on it, so the bridge never came online. 7.0.0 had this too.
- The example display message in MESSAGES.md was not valid JSON.
- The MQTT client no longer leaves threads behind when the connection to the broker drops while it is being set up.
  Paho 1.2.5, the last release of its MQTT 3 client, leaked one on every such drop; on a flapping line they piled up.
- After a reconnect to the MQTT broker, a subscribe that got no answer could block every incoming command for good,
  while the bridge kept reporting itself online. Calls to the broker now give up after 10 seconds, the resubscribe no
  longer runs on the thread that executes commands, and a failed resubscribe is tried again every 5 seconds (at most
  5 times) as long as the connection stays up.
- Commands that arrive while the central unit is unreachable wait for it at most 30 seconds from their arrival, and
  are then dropped with a warning (`MQTT topic '...' not executed: waited 30 seconds for the central unit`). Before,
  commands queued during a long outage could still be executed minutes later, once the line came back.
- A corrupt message from the central unit no longer costs the messages around it: the bridge resynchronises on the
  next message start instead of dropping everything it received. A wrong checksum is now logged as a warning
  (`Receive - Skipping bytes with a wrong checksum`) instead of an error.
- The bridge no longer gives up on a central unit that stays unreachable for more than 10 minutes. Before, it
  stopped trying after 10 minutes, until the next state refresh (`TELETASK_PUBLISH_STATES_INTERVAL`) or the next
  command woke it up.
- After a reconnect to the central unit the bridge could stop reporting state changes for good, while it kept
  reporting itself online. That happened when the line faltered again right after the reconnect and the central unit
  did not answer the request for its state changes. The bridge now reconnects when that request fails
  (`Could not ask the central unit for its state changes, reconnecting`).
- A bridge that starts before the MQTT broker can be reached now keeps trying every 10 seconds until the broker
  answers, and starts then. Before, the container kept running without ever connecting. With
  `TELETASK_MQTT_EXIT_ON_DISCONNECT` the bridge exits instead, like it does when the connection is lost.
- A startup that fails for another reason, such as a `TELETASK_MQTT_PORT` that is no port number, now ends the process
  with exit code 1 instead of leaving a container running that never became a bridge.
- The licence in the POM said LGPLv3; jeletask is GPLv3, as `LICENSE.md` has always said.
